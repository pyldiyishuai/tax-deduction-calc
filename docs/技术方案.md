# 个税专项附加扣除计算器 · 技术方案

---

## 一、产品定位

### 用户是谁

| 画像 | 场景 | 核心诉求 |
|---|---|---|
| 有孩子的职场人 | 不知道能扣多少 | 一年能省多少钱 |
| 租房一族 | 不知道租金能扣 | 我这种情况填多少 |
| 有房贷的人 | 租房/房贷怎么选 | 哪个更划算 |
| 独生子女 | 赡养老人怎么填 | 3,000 还是 1,500 |
| 高收入人群 | 想优化税负 | 怎么分配最省 |
| 忘记填报的人 | 汇算时才发现 | 还能补吗 |

### 为什么这个需求值钱

1. **覆盖率极高**：有孩子、租房、有房贷、赡养老人的群体加起来覆盖绝大多数城镇职工
2. **纯损失型痛点**：不填就是白交钱，没有争议、不需要说服
3. **可量化**：能算出精确的「少缴 X 元」，说服力极强
4. **每年重复**：每年 12 月确认、次年 3–6 月汇算，周期性回访
5. **政策刚变过**：2023 年三项标准提高，大量用户还不知道

### 与同类产品的差异

现有的个税计算器大多是「工资算个税」，不做专项附加扣除的逐项拆解。
本工具的差异点：
- 七项逐项展示，每项标出「抵税 ¥X」
- 填 vs 不填的对比条
- 边际税率教育（让用户理解「不是抵税是减基数」）
- 夫妻分配算例

## 二、算法结构

### 2.1 主链路

```
应纳税所得额 = 年收入 − 基本减除费用 − 社保公积金个人部分 − 专项附加扣除
应缴个税     = 应纳税所得额 × 税率 − 速算扣除数
```

基本减除费用 = 60,000 元/年（5,000 元/月），人人都有，不需要填报。

### 2.2 税率表（综合所得年度）

| 级数 | 应纳税所得额 | 税率 | 速算扣除数 |
|---|---|---|---|
| 1 | ≤ 36,000 | 3% | 0 |
| 2 | 36,000–144,000 | 10% | 2,520 |
| 3 | 144,000–300,000 | 20% | 16,920 |
| 4 | 300,000–420,000 | 25% | 31,920 |
| 5 | 420,000–660,000 | 30% | 52,920 |
| 6 | 660,000–960,000 | 35% | 85,920 |
| 7 | > 960,000 | 45% | 181,920 |

速算扣除数 = 前几档的累进差额，用它可以一步算出总税额，
不用逐档累加。两者结果必须一致（测试里有校验）。

### 2.3 七项扣除的实现差异

这是本工具的核心复杂度——七项的算法各不相同：

| 项目 | 类型 | 算法 |
|---|---|---|
| 婴幼儿照护 | count | 数量 × 2,000 × 12 |
| 子女教育 | count | 数量 × 2,000 × 12 |
| 继续教育 | choice | 选档 × 12（400 或 300） |
| 大病医疗 | amount | min(max(自付−15,000, 0), 80,000) |
| 住房贷款利息 | toggle | 有则 1,000 × 12 |
| 住房租金 | choice | 选档 × 12（1,500/1,100/800） |
| 赡养老人 | elder | 独生 3,000，非独生 1,500，× 12 |

用 `type` 字段区分，`buildDeductions` 里一个 if-else 链处理。
新增项目只需加一个分支。

### 2.4 边际税率的两个用途

```js
var rate = marginalRate(taxableFull || taxableBase);
```

**用途 1**：算每项扣除的抵税价值
```js
taxValue = item.yearly * rate
```

**用途 2**：教育用户理解「扣除 ≠ 抵税」

这里有个微妙点：**用扣除后还是扣除前的应纳税所得额算边际税率？**

答案是用**扣除后**的。因为扣除后的所得额才决定你实际适用的最高档。
比如 60 万收入，扣除前应纳税所得额 430,800（30% 档），
扣除 73,200 后变成 357,600（25% 档）——实际边际税率是 25%。

但这里有个循环依赖：抵税价值需要边际税率，而边际税率取决于扣除后的所得额，
扣除后的所得额又取决于扣除额。解决方法是**先算总额再算边际税率**，
因为边际税率只取决于总额，不取决于单项。

### 2.5 分档明细的算法

```js
for each bracket:
  if (taxable <= lower) break
  upper = min(bracket.upTo, taxable)
  amount = upper - lower
  tax = amount × bracket.rate
  lower = upper
```

目的不是算总税额（速算法更快），而是**可视化每一档的贡献**。
用户看到「36,000 按 3%，34,800 按 10%」，比看到「4,560」更理解累进制的含义。

## 四、扩展点

### 4.1 年终奖单独计税对比（最优先）

**场景**：年终奖是单独计税还是并入综合所得更划算。

**算法**：
- 单独计税：年终奖 ÷ 12 查月度税率表，税额 = 年终奖 × 税率 − 速算扣除
- 并入综合所得：年终奖加进年收入，按年度税率表算

两者取小。**关键**：年终奖有「多发 1 元多缴几千」的临界点陷阱。

**价值**：这是搜索量极大的独立话题，可以直接做成关联产品
（`bonus-tax-calc` 已经单独做了）。

### 4.2 夫妻分配最优化

**场景**：一个孩子的 2,000 元额度、房贷利息、赡养老人，
在夫妻之间怎么分配最省税。

**算法**：对每个可分配项目，比较「全给 A」「全给 B」「各 50%」三种方案，
按两人各自的边际税率算总节税，取最大。

**约束**：
- 子女教育/婴幼儿：可 50/50 或 100/0
- 房贷利息：只能一方 100%
- 赡养老人：各自的父母各自扣（不能给对方父母扣）
- 住房租金：夫妻同城只能一方扣

**价值**：这是本工具最自然的进阶功能，也是最容易做出差异化的地方。

### 4.3 月度预扣预缴明细

**场景**：想知道每月工资条上的个税是怎么算出来的。

**算法**：累计预扣法
```
本月应预扣 = (累计收入 − 累计减除 − 累计专项 − 累计已预扣) × 税率 − 速算扣除
```

**注意**：累计预扣法下，年初税率低、年末税率高，
同样月薪的人每月到手不一样。这个反直觉的现象很值得解释。

### 4.4 汇算清缴退补税

**场景**：次年 3–6 月，算算自己是退税还是补税。

**算法**：
```
应退/补 = 全年已预扣 − 全年应纳税额
```

**常见退税情形**：
- 有专项附加扣除但没及时填报
- 年中入职（只工作了几个月）
- 有多处工资薪金（重复扣了 6 万减除费用）
- 有劳务报酬（预扣率高）

### 4.5 报税服务线索（变现）

**已有**：`APP.FEATURES.taxLead`、`#leadBox`、`leadSubmit`。

**触发条件**：`income > 300000`。高收入用户的报税需求更复杂，付费意愿更强。

**合规注意**：不做「帮你少缴税」的承诺，只做「协助申报」。
任何涉及虚构扣除项的方案都不能碰。

## 七、监控指标

| 指标 | 意义 |
|---|---|
| 收入分桶分布 | 判断用户结构，决定内容深度 |
| 各项扣除的启用率 | 哪一项最被忽略（教育机会） |
| 平均启用项数 | 反映用户的认知完整度 |
| 边际税率分布 | 高税率用户的占比 = 变现潜力 |
| 房贷+租金冲突率 | 反映用户的误解程度 |
| 节税金额分桶 | 判断「痛点强度」 |
| 线索转化率 | 收入 |

**「平均启用项数」是最有意思的指标**。
如果平均只有 1.5 项，说明大量用户漏填了其他项——
这就是内容运营的机会（做「你可能还漏了这几项」的提示）。

## 八、已知坑

### 坑 1：`activeCount` 忘了返回

`buildDeductions` 最初返回 `{list, yearly, monthly}`，
但 `buildTips` 里用了 `ded.activeCount`，
导致提示文案变成「填了 **undefined** 项扣除」。

这类 bug 不会抛异常，只会在文案里静静显示 `undefined`。
**测试必须显式检查 `indexOf('undefined') === -1`。**

### 坑 2：边际税率要用扣除后的所得额

用扣除前的会高估抵税价值。60 万收入的例子：
扣除前 30% 档，扣除 73,200 后降到 25% 档。
如果按 30% 算抵税，会多算 20%。

### 坑 3：大病医疗的双重限制

```js
var over = Math.max(paid - 15000, 0);   // 门槛
yearly = Math.min(over, 80000);          // 封顶
```

两个都要，缺一个就错。
`paid = 15000` 时结果必须是 0，`paid = 15001` 时是 1。

### 坑 4：社保金额不钳制会出负数

```js
var social = Math.min(Math.max(n(f.social), 0), income);
```

不钳制的话，`taxable.base` 会显示负值。
虽然 `taxOf` 里有 `Math.max(t, 0)` 兜住税额，
但界面上的「应纳税所得额 −50,000」很难看。

### 坑 5：Hero 文案与默认值算例不一致

Hero 最初写「一年少缴 5,160 元」，默认值算出来是 7,320。
这种不一致是第一眼就能看出来的可信度问题。

**规则：改默认值或改算法后，必须回头核对 Hero 里的每一个数字。**

### 坑 6：子女数量步进器只管 UI

`type="number"` 的输入框用户可以手打 99。
core 层的 `Math.min(Math.max(Math.round(n(f.children)), 0), def.max)` 必须再钳一次。

### 坑 7：住房租金和房贷的互斥只在 UI 层提示

`Form.updateHints()` 检测到冲突时显示红字，
但**计算仍然把两项都算进去了**。

这是有意的——如果直接禁止，用户会困惑「为什么我勾不上」。
更好的做法是：算出结果 + 明确警告 + 告诉用户应该保留哪个。
但理想的交互是算两遍，给用户看「只留房贷」和「只留租金」两个结果。

### 坑 8：年终奖不进本工具

年终奖可以单独计税，也可以并入综合所得。
本工具只算综合所得，不含年终奖。

**必须在免责声明里写清楚**，否则用户会拿工资条来对不上。
